# אבטחה

עמוד זה מתאר כיצד LookSee מגנה על מופע ועל מה המפעיל צריך לשים לב. הוא משלים את [מדיניות האבטחה](https://github.com/okoflow/looksee/blob/main/SECURITY.md) שבמאגר, שעוסקת בדיווח על פגיעויות.

## חשבונות וסשנים

- קיים חשבון אחד: הבעלים, שנוצר בעמוד ההגדרה הראשונית אחרי ההפעלה הראשונה. אין הרשמה עצמית ואין ניהול משתמשים.
- הסיסמאות מגובבות (hashed) באמצעות Argon2. טופס ההגדרה הראשונית דורש שמונה תווים לפחות עם ספרה אחת ואות רישית אחת.
- ההתחברות מגדירה עוגייה `looksee_session`: `HttpOnly`, `SameSite=Lax`, תקפה לשבעה ימים, ו-`Secure` כאשר `AUTH_COOKIE_SECURE=true`. ההתנתקות מוחקת את העוגייה; האסימון עצמו נשאר תקף עד שהוא פוקע, ולכן ראו בעוגייה שדלפה סיבה להחליף את `SECRET_KEY`.
- כל נתיב API מלבד `/health`, `/auth/*` והתיעוד האינטראקטיבי דורש את העוגייה.

> [!WARNING]
> עד שחשבון הבעלים קיים, נקודת הקצה של ההגדרה הראשונית פתוחה לכל מי שיכול להגיע ל-Studio או ל-API. צרו את הבעלים מיד אחרי ההפעלה הראשונה, או הפעילו את הסטאק כשהפורטים חסומים בחומת אש ופתחו אותם לאחר מכן.

## סודות

ה-API גוזר שני מפתחות מסוד שורש אחד: מפתח חתימה לאסימוני סשן ומפתח הצפנה לאישורי גישה שמורים. סוד השורש הוא `SECRET_KEY` כשהוא מוגדר; אחרת ה-API מייצר אחד בהפעלה הראשונה ושומר אותו ב-`SECRET_KEY_FILE` על ה-volume בשם `api_keys` עם הרשאות לבעלים בלבד.

- אובדן הסוד מנתק כל משתמש והופך אישורי גישה שמורים לבלתי-קריאים. גבו את ה-volume בשם `api_keys` או הגדירו את `SECRET_KEY` במפורש.
- תוכני אישורי הגישה (אסימוני בוט, כתובות webhook, סיסמאות SMTP ו-MQTT) מוצפנים במנוחה ולעולם אינם מוחזרים על ידי ה-API; הרשימה מציגה שם ותקציר לא-סודי. הם מפוענחים רק כשפעולה מוסרת הודעה.
- החלפת `SECRET_KEY` מבטלת סשנים ואת הצפנים הקיימים של אישורי הגישה; הזינו את אישורי הגישה מחדש לאחר מכן.

## מה דפדפנים יכולים לראות

Studio מחדיר את תצורת זמן הריצה שלו לכל עמוד, כולל `RUNTIME_MEDIAMTX_MEDIA_USER` ו-`RUNTIME_MEDIAMTX_MEDIA_PASSWORD`, מכיוון שהדפדפן מנגן וידאו חי ומפרסם מצלמות רשת ישירות מול MediaMTX. כל מי שיכול לטעון את עמוד ההתחברות של Studio יכול לקרוא ערכים אלה ולהשתמש בהם כדי לקרוא או לפרסם כל נתיב מצלמה ב-MediaMTX.

השלכות לפריסה:

- שנו את `MTX_MEDIA_PASSWORD` מערך הדוגמה, וראו בה סיסמה המשותפת לכל מי שיכול להגיע ל-Studio.
- השאירו את פורטי MediaMTX (`8554`, `8889`, `8189/udp`) נגישים רק מהרשתות שבהן נמצאים המצלמות ומשתמשי Studio.
- אל תשתמשו בסיסמת MediaMTX בשום מקום אחר.

## חשיפה לרשת

| חשוף לכל הממשקים | Loopback בלבד |
| --- | --- |
| Studio `3000`, API `8000`, RTSP `8554`, WebRTC `8889` ו-`8189/udp` | PostgreSQL `5432`, Valkey `6379`, API הבקרה של MediaMTX `9997` |

API הבקרה של MediaMTX מקבל בקשות לא מאומתות מ-loopback ומטווחי כתובות פרטיות; הוא מאוגד ל-loopback כדי שרק קונטיינר ה-API והמארח יגיעו אליו. אל תפרסמו את פורט `9997`.

מדיניות ה-CORS של ה-API מאפשרת `localhost` ו-`127.0.0.1` כברירת מחדל. הגדירו את `CORS_ORIGIN_REGEX` בפריסה בדיוק למקור של Studio, ואל תרחיבו אותו לכל מקור: ה-API מקבל בקשות חוצות-מקור עם פרטי אימות (credentials).

## פעולות ותעבורה יוצאת

פעולות Webhook, Telegram, Discord, Slack, MQTT ודוא"ל מתחברות לכתובות שהוגדרו בתהליך העבודה או באישור הגישה. אין רשימת היתרים, ולכן משתמש שיכול לערוך תהליכי עבודה יכול לגרום ל-API להתחבר לכתובות פנימיות. רק הבעלים יכול לערוך תהליכי עבודה; זכרו זאת כשאתם נותנים למישהו את סיסמת הבעלים.

תמונות מצב מוגשות ב-`/snapshots/<file>` לכל בקשה עם אסימון סשן תקף. הן נשמרות לא מוצפנות על ה-volume בשם `api_snapshots`.

## בסיס מומלץ

- שנו כל סיסמת דוגמה; הגדירו `SECRET_KEY` או גבו את `api_keys`.
- סיימו את ה-TLS בפרוקסי הפוך לפני Studio וה-API, הגדירו `AUTH_COOKIE_SECURE=true` וכוונו את כתובות `RUNTIME_*` לכתובות הציבוריות.
- הגבילו את `CORS_ORIGIN_REGEX` למקור של Studio.
- חסמו בחומת אש את פורטי MediaMTX לרשתות המצלמות והמשתמשים בלבד.
- השאירו את הסטאק ברשת מהימנה. אל תחשפו אותו, או את המצלמות שמאחוריו, לאינטרנט הציבורי.

[פריסה](deployment.md) מציג תצורת פרוקסי הפוך שמיישמת בסיס זה.
