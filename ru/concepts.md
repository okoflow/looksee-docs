# Основные понятия

Эта страница объясняет словарь, которым пользуется остальная документация:
рабочие процессы и узлы, события и то, как их производят модели, камеры и
запуски, а также две редакции.

## Рабочие процессы

Рабочий процесс — это граф, описывающий одну задачу аналитики: за какой
камерой наблюдать, какую модель запускать, какие детекции важны и что с ними
делать. Рабочие процессы создаются и редактируются в Studio и хранятся API.
Рабочий процесс либо запущен (**Active**), либо остановлен (**Off**); **Run**
в редакторе запускает его, **Stop** останавливает.

У рабочего процесса есть имя, необязательное описание и граф из узлов и
связей. На холст можно добавлять комментарии для документирования; они не
выполняются.

## Узлы и связи

Узлы — это блоки на холсте. У каждого узла есть тип и набор полей, которые
редактирует инспектор справа. Типы делятся на четыре роли:

| Роль | Узлы | Назначение |
| --- | --- | --- |
| Источник | Camera | Откуда берутся кадры |
| Детекция | Detect | Какая модель работает и какие из её событий проходят дальше |
| Фильтр | If / Else, Class, Size, Zone, Schedule, Debounce; Count, Line crossing, Dwell в редакции Enterprise | Решает, продолжает ли событие путь |
| Действие | Alert, Snapshot, Webhook, Telegram, Email, MQTT, Discord; Slack в редакции Enterprise | Делает что-то с событием |

Связи соединяют узлы слева направо. Camera соединяется ровно с одним Detect.
Detect разветвляется на любое число фильтров и действий. У каждого фильтра
два выхода, **If** и **Else**: событие, прошедшее фильтр, продолжает путь по
**If**, не прошедшее — по **Else**. Связь, проведённая от фильтра без выбора
ветки, следует по **If**. Snapshot — единственное действие с выходом:
действия, подключённые после него, получают сделанный им снимок. Остальные
действия — конечные точки.

[Узлы](nodes.md) перечисляют каждый узел с его полями и ограничениями.

## События

Детекция производит события, и именно события текут по графу. Сервис
инференса сообщает детекции для каждого обработанного кадра: метку, рамку,
уверенность и идентификатор трекинга. API группирует детекции кадра по метке
и выводит по одному событию на метку, названному по ней: `helmet`
становится `HELMET_DETECTED`, `space-empty` — `SPACE_EMPTY_DETECTED`.
Манифест модели может переименовать событие метки или подавить его.
Фиксированного списка типов событий нет; словарь задают установленные вами
модели.

Событие несёт свой тип, камеру, метку времени, размер кадра, стоящие за ним
детекции и их количество. Фильтры смотрят на эти поля: Zone проверяет центр
каждой детекции относительно многоугольника, Class проверяет метки, Size —
площадь рамки, If / Else сравнивает тип, класс, количество или наибольшую
уверенность.

В граф попадает каждое событие; три окна сдерживают повторы:

- **Пауза между событиями** (`EVENT_COOLDOWN_SECONDS`, по умолчанию
  2 секунды) ограничивает, как часто живая лента событий показывает один тип
  события на одной камере. События в графе она не задерживает.
- **Debounce** (подавление повторов) — фильтр, который вы ставите там, где
  нужно, со своим окном.
- **Пауза между оповещениями** (cooldown) — поле действия Alert; применяется
  только к истории оповещений.

Состояние фильтров и паузы живут в памяти процесса API. Они сбрасываются при
перезапуске API и не разделяются между репликами API.

## Камеры и запуски

Каждый узел Camera в рабочем процессе становится записью камеры со статусом:

| Статус | Значение |
| --- | --- |
| **Pending** | Рабочий процесс запущен, но сервис инференса ещё не подтвердил поток |
| **Active** | Кадры обрабатываются |
| **Error** | Поток отказал; API повторяет попытки с растущей задержкой |
| **Off** | Рабочий процесс остановлен |

Монитор показывает те же состояния как **Starting**, **Live**, **Error** и
**Off**; API возвращает их как `pending`, `active`, `error` и `disabled`.

Запуск рабочего процесса просит MediaMTX открыть по одному пути на камеру, а
сервис инференса — поднять по одному воркеру на камеру. Каждый старт — это
*запуск* с номером ревизии, поэтому остановленную или перенастроенную камеру
не может воскресить запоздавшее сообщение из старого запуска. Цикл
согласования в API повторно публикует желаемое состояние каждые 30 секунд —
именно он возвращает камеры после перезапуска любого сервиса.

Изменение настроек детекции запущенного рабочего процесса применяется на
месте. Изменение источника камеры перезапускает её воркер.

[Камеры](cameras.md) описывают типы источников и то, как с ними работает
MediaMTX.

## Модели

Модель — это файл ONNX плюс манифест, размещённые в `models/`. Манифест
объявляет метки, которые производит модель, и, при желании, отображаемое
имя, рекомендуемый порог уверенности и переопределения событий. API
обнаруживает пакеты моделей во время работы; узлы Detect выбирают модель из
этого каталога.

Детекция выполняется с частотой, заданной узлом Detect
(**Checks per second**), а не с частотой кадров камеры. Между проверками
объекты отслеживаются, так что фильтры, которым нужна идентичность объекта,
такие как пересечение линии и время пребывания, могут следить за одним
объектом во времени.

[Модели](models.md) описывают формат манифеста и экспорт.

## Учётные данные

Действия, которые обращаются к внешнему сервису (Telegram, Discord,
электронная почта, MQTT, Slack), ссылаются на учётные данные, а не хранят
токен сами. Учётные данные хранятся в зашифрованном виде, показываются только
по имени и несекретной сводке и разрешаются в момент доставки, поэтому смена
токена вступает в силу немедленно.

[Действия и интеграции](actions-and-integrations.md) описывают каждый тип.

## Редакции

Редакция Community содержит всё за пределами каталога `ee/` репозитория и
лицензирована под Apache-2.0. Редакция Enterprise добавляет фильтры Count,
Line crossing и Dwell и действие Slack; в палитре узлов они показаны с
замком, пока не настроен лицензионный ключ. Обе редакции поставляются в одних
и тех же образах. Подробности — в разделе [Редакция Enterprise](enterprise.md).
