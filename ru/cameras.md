# Камеры

Узел Camera сообщает LookSee, откуда берутся кадры. MediaMTX принимает каждый
источник, отдаёт его сервису инференса как один путь RTSP на камеру и раздаёт
тот же поток браузерам по WebRTC для живого монитора.

## Типы источников

| Тип источника | Поле | Как принимается |
| --- | --- | --- |
| **RTSP** | URL `rtsp://` или `rtsps://` | MediaMTX забирает поток по запросу. Большинство IP-камер и видеорегистраторов. |
| **RTMP** | URL `rtmp://` или `rtmps://` | MediaMTX забирает поток по запросу. |
| **SRT** | URL `srt://` | MediaMTX забирает поток по запросу. |
| **Browser webcam** | нет | Режим публикации. Studio публикует камеру браузера по WebRTC (WHIP) в MediaMTX. |
| **WHEP** | URL `http://`, `https://`, `whep://` или `wheps://` | MediaMTX забирает удалённую конечную точку WebRTC. |
| **File** | ключ файла | Видео из библиотеки файлов кэшируется локально и проигрывается по кругу как живой поток. |

Забираемые источники работают по запросу: MediaMTX подключается к
вышестоящему источнику, когда путь запрашивает сервис инференса или браузер,
и отключается через десять секунд после ухода последнего читателя. Учётные
данные для вышестоящего источника указываются в URL,
`rtsp://user:password@192.168.1.30:554/stream1`, и остаются на сервере.

## RTSP, RTMP и SRT

Введите URL, который публикует ваша камера или кодер. Замечания для типичных
случаев:

- Используйте дополнительный поток камеры (720p или ниже), а не основной.
  Детекция работает на нескольких кадрах в секунду и не выигрывает от 4K, а
  его декодирование расходует CPU.
- H.264 декодируется везде. H.265 подходит для детекции, но браузеры не
  воспроизводят его по WebRTC, поэтому живой монитор остаётся чёрным, хотя
  оповещения приходят.
- MediaMTX забирает RTSP по TCP. Если камера предлагает только UDP, поставьте
  перед ней ретранслятор, который умеет TCP.
- Камера в другой сети должна быть доступна с машины, на которой работает
  LookSee; браузер никогда не подключается к камере напрямую.

## Веб-камера браузера

У камеры с типом источника **Browser webcam** нет URL. Когда рабочий процесс
запущен и открыт редактор или монитор, Studio запрашивает разрешение на
использование веб-камеры и публикует её в MediaMTX из браузера. Для таких
камер монитор показывает кнопки **Publish** (публиковать) и **Stop publish**
(остановить публикацию). Закрытие вкладки останавливает поток; камера
возвращается в состояние **Pending**, пока браузер не начнёт публиковать
снова.

Браузер публикует на `WEBRTC_HOST_IP` через порт `8889`, и ему нужен открытый
порт ICE `8189/udp`; см. раздел [Сеть](#сеть).

## Видеофайлы

Камера **File** проигрывает по кругу объект из библиотеки файлов — это удобно
для проверки рабочего процесса на записи. Библиотека файлов — это
S3-совместимый бакет, настроенный переменными `S3_*`; она создана для
Cloudflare R2 и работает с MinIO или любой другой конечной точкой S3. Без
настроенного бакета выбор **Assets** и конечные точки `/assets` отключены.

Файлы загружаются через Studio или `POST /assets`. При запуске API скачивает
объект в том медиакэша, из которого MediaMTX читает его и проигрывает по
кругу с помощью ffmpeg. Ключи объектов ограничены буквами, цифрами, `.`, `_`,
`-` и `/`, потому что они попадают внутрь команды ffmpeg.

## MediaMTX

MediaMTX работает как сервис `mediamtx` с конфигурацией в
`docker/mediamtx/mediamtx.yml`. LookSee управляет его путями через
управляющий API на порту `9997`; сам файл задаёт только протоколы и
аутентификацию:

- RTSP на `8554` по TCP; WebRTC на `8889` с ICE на `8189/udp`. Слушатели
  RTMP, HLS и SRT выключены, что не мешает забирать потоки с вышестоящих
  источников RTMP и SRT.
- Один пользователь, `MTX_MEDIA_USER` с паролем `MTX_MEDIA_PASSWORD`, может
  читать и публиковать. Его используют сервис инференса и браузеры. Studio
  передаёт эти учётные данные браузеру для воспроизведения, поэтому считайте
  их реквизитами доступа для доверенной сети, а не серверным секретом.
- Управляющий API открыт для петлевого интерфейса и диапазонов частных сетей
  без аутентификации; compose привязывает его к `127.0.0.1`.

Имя пути каждой камеры — её идентификатор. Сервис инференса читает
`rtsp://mediamtx:8554/<camera id>`, а браузеры воспроизводят
`http://<WEBRTC_HOST_IP>:8889/<camera id>/whep`.

## Сеть

Живое видео доходит до браузера по WebRTC, которому нужно больше, чем один
открытый веб-порт:

| Порт | Протокол | Кто подключается |
| --- | --- | --- |
| `8889` | TCP | Браузеры — для сигнализации и воспроизведения WebRTC (WHEP) и публикации веб-камеры (WHIP) |
| `8189` | UDP | Браузеры — для медиапотока WebRTC (ICE) |
| `8554` | TCP | Кодеры, которые публикуют RTSP в путь камеры типа **Browser webcam** (режим публикации); для забираемых источников не нужен |

`WEBRTC_HOST_IP` должен быть адресом, доступным браузерам: `127.0.0.1` на
ноутбуке, адрес в локальной сети на сервере. MediaMTX объявляет его в
кандидатах ICE; при неверном значении монитор подключается, а затем
показывает **Connection disconnected**. Раздел [Развёртывание](deployment.md)
описывает обратные прокси и TLS.

## Статус камеры

Монитор показывает значок статуса рядом с именем камеры, а список рабочих
процессов — статус каждого рабочего процесса.

- **Pending** (**Starting** в мониторе): воркер запускается. Для забираемых источников первый кадр
  обычно приходит за несколько секунд; сервис инференса прекращает ожидание
  через `FIRST_FRAME_TIMEOUT_SECONDS` (30 секунд) и сообщает об ошибке.
- **Active** (**Live** в мониторе): кадры идут.
- **Error**: поток отказал или замер на 30 секунд. API повторяет попытки с
  задержкой, которая удваивается от 30 секунд до 5 минут. Причина показана в
  мониторе и в журналах `api` и `inference`.
- **Off**: рабочий процесс остановлен.

[Устранение неполадок](troubleshooting.md) перечисляет частые причины
**Pending** и **Error**.
