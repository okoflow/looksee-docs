# Безопасность

Эта страница описывает, как LookSee защищает экземпляр и о чём должен
позаботиться оператор. Она дополняет
[политику безопасности](https://github.com/okoflow/looksee/blob/main/SECURITY.md)
в репозитории, которая описывает порядок сообщения об уязвимостях.

## Учётные записи и сессии

- Существует одна учётная запись: владелец, создаваемый на странице
  первоначальной настройки после первого запуска. Саморегистрации и
  управления пользователями нет.
- Пароли хешируются Argon2. Форма настройки требует не менее восьми символов
  с одной цифрой и одной заглавной буквой.
- Вход выставляет cookie `looksee_session`: `HttpOnly`, `SameSite=Lax`, срок
  действия семь дней, `Secure` при `AUTH_COOKIE_SECURE=true`. Выход удаляет
  cookie; сам токен остаётся действительным до истечения срока, поэтому
  утечку cookie считайте поводом сменить `SECRET_KEY`.
- Каждый маршрут API, кроме `/health`, `/auth/*` и интерактивной
  документации, требует cookie.

> [!WARNING]
> Пока учётной записи владельца нет, конечная точка первоначальной настройки
> открыта любому, кто может достучаться до Studio или API. Создайте владельца
> сразу после первого запуска или запускайте стек с закрытыми брандмауэром
> портами и открывайте их потом.

## Секреты

API выводит два ключа из одного корневого секрета: ключ подписи токенов
сессий и ключ шифрования сохранённых учётных данных. Корневой секрет — это
`SECRET_KEY`, когда он задан; иначе API генерирует его при первом запуске и
сохраняет в `SECRET_KEY_FILE` на томе `api_keys` с правами только для
владельца файла.

- Потеря секрета завершает сессии всех пользователей и делает сохранённые
  учётные данные нечитаемыми. Делайте резервную копию тома `api_keys` или
  задайте `SECRET_KEY` явно.
- Содержимое учётных данных (токены ботов, URL вебхуков, пароли SMTP и MQTT)
  шифруется при хранении и никогда не возвращается API; список показывает имя
  и несекретную сводку. Оно расшифровывается только в момент доставки
  действием.
- Смена `SECRET_KEY` делает недействительными сессии и существующие
  шифртексты учётных данных; после неё введите учётные данные заново.

## Что видят браузеры

Studio внедряет свою конфигурацию времени выполнения в каждую страницу,
включая `RUNTIME_MEDIAMTX_MEDIA_USER` и `RUNTIME_MEDIAMTX_MEDIA_PASSWORD`,
потому что браузер воспроизводит живое видео и публикует веб-камеры напрямую
в MediaMTX. Любой, кто может загрузить страницу входа Studio, может прочитать
эти значения и использовать их, чтобы читать или публиковать любой путь
камеры в MediaMTX.

Следствия для развёртывания:

- Смените `MTX_MEDIA_PASSWORD` со значения из примера и считайте его
  известным каждому, кто может достучаться до Studio.
- Держите порты MediaMTX (`8554`, `8889`, `8189/udp`) доступными только из
  сетей, где находятся камеры и пользователи Studio.
- Не используйте пароль MediaMTX где-либо ещё.

## Сетевая доступность

| Открыто на всех интерфейсах | Только петлевой интерфейс |
| --- | --- |
| Studio `3000`, API `8000`, RTSP `8554`, WebRTC `8889` и `8189/udp` | PostgreSQL `5432`, Valkey `6379`, управляющий API MediaMTX `9997` |

Управляющий API MediaMTX принимает неаутентифицированные запросы с петлевого
интерфейса и из диапазонов частных адресов; он привязан к петлевому
интерфейсу, чтобы до него доходили только контейнер API и хост. Не
публикуйте порт `9997`.

Политика CORS API по умолчанию разрешает `localhost` и `127.0.0.1`. В
развёртывании задайте `CORS_ORIGIN_REGEX` точно равным origin Studio и не
расширяйте его на все источники: API принимает cookie в межсайтовых
запросах.

## Действия и исходящий трафик

Действия Webhook, Telegram, Discord, Slack, MQTT и Email подключаются к
адресам, настроенным в рабочем процессе или учётных данных. Списка
разрешённых адресов нет, поэтому пользователь, который может редактировать
рабочие процессы, может заставить API подключаться к внутренним адресам.
Редактировать рабочие процессы может только владелец; помните об этом,
передавая кому-либо пароль владельца.

Изображения снимков отдаются по `/snapshots/<file>` любому запросу с
действительным токеном сессии. Они хранятся в незашифрованном виде на томе
`api_snapshots`.

## Рекомендуемый минимум

- Смените каждый пароль из примера; задайте `SECRET_KEY` или делайте
  резервную копию `api_keys`.
- Терминируйте TLS в обратном прокси перед Studio и API, установите
  `AUTH_COOKIE_SECURE=true` и направьте URL `RUNTIME_*` на публичные адреса.
- Ограничьте `CORS_ORIGIN_REGEX` значением origin Studio.
- Закройте порты MediaMTX брандмауэром для всех, кроме сетей камер и
  пользователей.
- Держите стек в доверенной сети. Не открывайте его и камеры за ним в
  публичный интернет.

Раздел [Развёртывание](deployment.md) показывает конфигурацию обратного
прокси, которая реализует этот минимум.
